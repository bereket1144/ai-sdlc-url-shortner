# Run API requirements

## Backlog status reconciliation (2026-10-05)

At the user's request, the reviewed stories use `stale` for historical criteria awaiting reconciliation with the current implementation and scope, and `deferred` for postponed work. Neither status means the behaviour is absent: existing code and known verification gaps are preserved.

Stories explicitly closed in this cleanup have `Status: done` and a dated disposition. This is a user-directed backlog closure, including superseded work, not a claim that a new QA or code review pass occurred or that every historical criterion was verified. Existing acceptance criteria are retained for reference. Other pre-existing statuses keep their meaning. See [ADR 0012](../../adr/0012-reconcile-platform-backlog-statuses.md).

## Request

The controller needs an HTTP API through which a requester starts a run from a written requirement and reads it back. It creates a run, refuses a bad request, and is fit for production use: a versioned path, one error format, bounded input, a recorded run state, and a way to read a run back.

## Ambiguities and assumptions

- **The API version is part of the URL path** (`/v1/...`), not a header. Chosen because it is visible in a browser, in `curl`, and in logs.
- **"Version" in RUN-6 is the run record's own version** (used to detect two writers changing the same run). It has nothing to do with the API version in RUN-3.
- **The error format is RFC 9457 problem details**, served as `application/problem+json`.
- **Input limit:** a requirement may be at most 20,000 characters. This number is an assumption; changing it needs the user's approval.
- **Run status has one value for now, `CREATED`.** More values are added by the stories that need them.
- **Times are UTC instants,** set by Hibernate when a run is saved. Tests check that a time falls between just before and just after the save.

## User stories and acceptance criteria

### RUN-1 Create a run

Status: done

As a requester, I want to submit a written requirement and receive a run ID, so that the platform can start work on it.

- AC-RUN-1.1 A create request with a JSON body `{"requirement": "<text>"}` returns 201 and a JSON body `{"id": "<uuid>"}`.
- AC-RUN-1.2 The ID is generated by the platform; the client does not supply one.
- AC-RUN-1.3 The run is saved in PostgreSQL: reading it back by ID returns the same requirement text.
- AC-RUN-1.4 A requirement longer than 255 characters is saved and read back unchanged.

### RUN-2 Reject an invalid create request

Status: done

As a requester, I want a bad create request refused clearly, so that I never start a run that has no usable requirement.

- AC-RUN-2.1 A body with a missing, null, empty, or whitespace-only `requirement` returns 400.
- AC-RUN-2.2 A body that is not valid JSON returns 400.
- AC-RUN-2.3 A request with no body returns 400.
- AC-RUN-2.4 No run is saved for any request refused under AC-RUN-2.1 to AC-RUN-2.3.
- AC-RUN-2.5 Creating a run directly with a null or blank requirement fails with `IllegalArgumentException` and the message `requirement must not be blank`.

### RUN-3 Version the API

Status: done

As an API client, I want the run endpoints under a version, so that the contract can change later without breaking me.

- AC-RUN-3.1 The create-run endpoint is served at `POST /v1/runs` and behaves as RUN-1 and RUN-2 describe.
- AC-RUN-3.2 A request to `/runs` without a version returns 404.
- AC-RUN-3.3 A request to a version that does not exist, such as `/v2/runs`, returns 404 and saves no run.
- AC-RUN-3.4 The health endpoint stays at `/actuator/health` and is not versioned.

### RUN-4 Return one error format

Status: done

As an API client, I want every error in the same structure, so that I can handle failures in one place.

- AC-RUN-4.1 A 400 caused by a bad field returns `application/problem+json` with `type`, `title`, `status` (400) and `detail`, and names the offending field (`requirement`).
- AC-RUN-4.2 A 400 caused by malformed JSON or a missing body returns the same structure.
- AC-RUN-4.3 A request to an unknown path returns 404 in the same structure.
- AC-RUN-4.4 A request with an unsupported content type returns 415 in the same structure.
- AC-RUN-4.5 An unexpected failure returns 500 in the same structure, with a generic `detail` that contains no stack trace, exception class, or exception message.
- AC-RUN-4.6 Every error response above has the content type `application/problem+json`.

### RUN-5 Bound the size of a requirement

Status: done

As the platform owner, I want input size limited, so that one request cannot exhaust memory, storage, or model budget.

- AC-RUN-5.1 A requirement of exactly 20,000 characters is accepted with 201.
- AC-RUN-5.2 A requirement of 20,001 characters returns 400 in the RUN-4 format, naming the field `requirement`, and saves no run.

### RUN-6 Record the state of a run

Status: done

As the platform, I want each run to record its status, when it was created, when it last changed, and its version, so that its progress can be told and two writers cannot overwrite each other unnoticed.

- AC-RUN-6.1 A new run has status `CREATED`.
- AC-RUN-6.2 `createdAt` is set once, when the run is first saved, to the current UTC time, and never changes afterwards.
- AC-RUN-6.3 `updatedAt` is set when the run is first saved and is never earlier than `createdAt`, and is set to the current time each time the run is changed.
- AC-RUN-6.4 `version` is 0 when the run is first saved and increases by 1 each time the run is changed.
- AC-RUN-6.5 Saving a change to a run that was based on an outdated version is rejected, and the stored run is unchanged.
- AC-RUN-6.6 A run saved before this change is still readable afterwards, with status `CREATED` and both times filled in.
- AC-RUN-6.7 The database schema change is a new migration; the existing migration is not edited.

### RUN-7 Read a run back

Status: done

As a requester, I want to read a run after creating it and be told where it lives, so that I can check on it without remembering anything but its ID.

Depends on RUN-3 (the path) and RUN-6 (the fields).

- AC-RUN-7.1 The 201 response to a create request has a `Location` header holding the path of the new run, `/v1/runs/<id>`.
- AC-RUN-7.2 `GET /v1/runs/<id>` for an existing run returns 200 with `id`, `requirement`, `status`, `createdAt`, `updatedAt` and `version`.
- AC-RUN-7.4 `GET /v1/runs/<id>` for an ID that does not exist returns 404 in the RUN-4 format.
- AC-RUN-7.5 `GET /v1/runs/<id>` where `<id>` is not a UUID returns 400 in the RUN-4 format.

### BUG-1 A very large request body is read in full before the length limit applies

Status: deferred

Disposition (2026-10-05): Early rejection of oversized request bodies is postponed as already intended by this story. The existing requirement-length validation remains in place.

As the platform owner, I want an oversized text refused before the whole of it is held in memory, so that one request cannot exhaust memory (RUN-5 only checks the length after the body is read). To be picked up much later; the exact maximum is decided then.

- AC-BUG-1.1 A request whose text field is far larger than the limit (several megabytes) is refused with 400 in the RUN-4 format, and the server does not read the whole text first.

## Out of scope

- Listing runs, paging, searching.
- Changing, cancelling, or deleting a run.
- Starting the graph or any agent work.
- Authentication, authorisation, and rate limiting.
- A client-supplied idempotency key on create.
- A request or correlation ID in responses and logs.
- A published API document (OpenAPI).
